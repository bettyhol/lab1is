# Експертна система діагностики аварій космічного корабля

## Мета роботи

Реалізувати навчальну експертну систему продукційного типу, яка за частково
відомими показниками бортових систем діагностує аварійну ситуацію. У цій роботі
використано тільки пряме логічне виведення зі стратегією пошуку завширшки.

## Предметна область

Система аналізує чотири типові ситуації на космічному кораблі:

- розгерметизацію корпусу;
- аварію енергосистеми;
- несправність системи зв'язку;
- критичний перегрів двигуна.

Це навчальна модель: вона демонструє причинно-наслідкові зв'язки продукційних
правил, а не моделює реальну фізику космічного апарата.

## Архітектура експертної системи

- **База знань** (`knowledge_base.py`) містить рівно 10 об'єктів `Rule` і не
  залежить від алгоритму виведення.
- **Моделі** (`models.py`) описують `Condition`, `Conclusion`, `Rule`, `Fact`,
  джерело факту, metadata змінних і запис протоколу.
- **Metadata змінних** (`variables.py`) визначає допустимі значення, українські
  підписи та ознаку базової вхідної змінної. Саме ця ознака дозволяє рушію не
  запитувати в користувача проміжні висновки.
- **Робоча пам'ять** (`working_memory.py`) зберігає всі змінні, ознаку
  ініціалізації, значення і джерело `USER`, `RULE` або `SCENARIO`.
- **Механізм прямого виведення** (`forward_engine.py`) є незалежним від CLI та
  отримує додаткові факти через callback `fact_provider(variable)`.
- **FIFO-черга** реалізована через `collections.deque`. Початкові й виведені
  змінні додаються в її кінець, а обробляються з початку.
- **Індекс умовних змінних** `rules_by_condition_variable` швидко знаходить
  правила, що залежать від поточної змінної.
- **Історія FIFO** зберігає фактичні `PUSH`, `POP`, snapshots черги та моменти
  спрацювання правил; її можна відкрити з меню результатів.
- **Протокол** зберігає кожну перевірку: правило, умову, очікуване та фактичне
  значення, `TRUE/FALSE/UNKNOWN` і факт спрацювання правила. Невідома змінна не
  позначається як хибна.
- **Логічний ланцюг** містить тільки правила, які реально спрацювали, у порядку
  їх спрацювання.
- **CLI** (`ui.py`) відповідає лише за взаємодію з користувачем і показ результатів.

Кожен виклик `infer()` створює нову робочу пам'ять, чергу та протокол, тому
результати попередньої діагностики не переносяться в нову.

## База знань

### R1

ЯКЩО `oxygen_level = low` І `pressure = falling`  
ТО `atmosphere_leak = detected`.

### R2

ЯКЩО `atmosphere_leak = detected` І `hull_sensor = damaged`  
ТО `incident = hull_breach`.

### R3

ЯКЩО `incident = hull_breach`  
ТО `recommended_action = isolate_damaged_compartment`.

### R4

ЯКЩО `generator = failed` І `battery_level = low`  
ТО `power_problem = critical`.

### R5

ЯКЩО `power_problem = critical`  
ТО `incident = power_system_failure`.

### R6

ЯКЩО `communication_module = failed` І `antenna = damaged`  
ТО `communication_problem = detected`.

### R7

ЯКЩО `communication_problem = detected`  
ТО `incident = communication_system_failure`.

### R8

ЯКЩО `engine_temperature = high` І `cooling_system = failed`  
ТО `engine_overheating = critical`.

### R9

ЯКЩО `engine_overheating = critical`  
ТО `incident = engine_cooling_failure`.

### R10

ЯКЩО `incident = engine_cooling_failure`  
ТО `recommended_action = emergency_engine_shutdown`.

## Алгоритм прямого виведення

1. Для нового сеансу створюється порожня робоча пам'ять.
2. Відомі початкові змінні додаються в кінець FIFO-черги.
3. Рушій дістає першу змінну та через індекс знаходить залежні правила.
4. Для кожного правила, яке ще не спрацювало, перевіряються всі умови.
5. Якщо невідомий базовий факт ще потрібний для потенційного спрацювання,
   рушій звертається до переданого callback. Проміжні змінні не запитуються.
6. Якщо всі умови істинні, висновок записується до робочої пам'яті з джерелом
   `RULE`, а його змінна додається в кінець FIFO-черги.
7. Обробка триває, доки черга не стане порожньою. Кожне правило може спрацювати
   не більше одного разу.
8. Основний результат — висновок останнього правила, яке спрацювало.

Таким чином висновок одного правила стає фактом і активує наступний рівень
продукційних правил у BFS-порядку.

## Приклад роботи

Для preset-сценарію **Hull Breach** задаються факти:

```text
oxygen_level = low
pressure = falling
hull_sensor = damaged
```

Рушій формує ланцюг, а не отримує його з hardcoded-сценарію:

```text
R1 -> atmosphere_leak = detected
R2 -> incident = hull_breach
R3 -> recommended_action = isolate_damaged_compartment

Логічний ланцюг: R1 -> R2 -> R3
Останній висновок:
recommended_action = isolate_damaged_compartment
```

З меню результатів можна переглянути логічний ланцюг, усю робочу пам'ять,
фактичну історію FIFO-черги та повний протокол перевірок.

## Межі реалізації

Реалізовано **лише forward chaining**. Зворотне (`backward chaining`) і гібридне
виведення навмисно не реалізовані; незалежні моделі та база знань дають змогу
додати їх у наступних лабораторних роботах без змішування з поточним рушієм.
